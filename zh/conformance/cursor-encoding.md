# 游标编码规范

## 1. 概述

本规范定义了 Contrix v1 同步游标的编码格式。游标是用于增量同步的**不透明令牌**。客户端 MUST NOT 解析或修改游标内容 — 客户端将游标视为在同步请求和响应之间传递的不透明字符串。

## 2. 游标格式

Contrix v1 游标是具有以下传输格式的不透明字符串：

```text
cx:cursor:<base64url>
```

其中 `<base64url>` 是服务器内部游标数据的 Base64URL 编码（无填充）。

### 2.1 客户端规则

- 客户端 MUST 将游标视为不透明字符串。
- 客户端 MUST NOT 解码、解析或修改游标内容。
- 客户端 MUST 存储最新的 `next_batch` 游标以用于恢复。
- 客户端 MUST 在下次同步请求中完全按原样使用游标。

### 2.2 服务器内部结构

服务器在 Base64URL 编码之前将游标内部结构编码为规范 JSON。内部结构由服务器定义，MAY 包含：

- 查询哈希或过滤器指纹
- 最后排序键 (HLC)
- 最后事件 ID
- 因果前沿（事件 ID 集合）
- 状态哈希
- 过期时间戳
- Space 位置

以下是**推荐的**内部 schema，用于互操作性 — 服务器 MAY 使用任何结构，只要传输格式为 `cx:cursor:<base64url>`：

```json
{
  "v": "1",
  "t": "2026-04-26T00:00:00.000Z",
  "s": {
    "cx:space:01js0sp0000000000000000000": {
      "p": ["cx:event:01js0ev0000000000000000000"],
      "o": "01970e589d21-0004-a13f9c2e",
      "h": "sha256:abc123..."
    }
  },
  "d": {
    "device-1": "cx:devmsg:01js0dm0000000000000000000"
  },
  "x": 1714080000000
}
```

| 字段 | 类型 | 必需 | 说明 |
|------|------|------|------|
| `v` | string | 是 | 游标版本，必须为 "1" |
| `t` | timestamp | 是 | 游标生成时间戳 |
| `s` | object | 是 | Space 位置映射 |
| `s.<space_id>.p` | array | 是 | 因果前沿（事件 ID 集合） |
| `s.<space_id>.o` | string | 是 | 时间线排序 HLC |
| `s.<space_id>.h` | hash | 是 | 该位置的状态哈希 |
| `d` | object | 否 | 设备位置映射 |
| `d.<device_id>` | string | 是 | 最后处理的消息 ID |
| `x` | integer | 是 | 过期时间戳（Unix 毫秒） |

## 3. 传输编码

服务器将其内部游标结构序列化为规范 JSON（UTF-8、无多余空白、键排序），然后使用无填充的 Base64URL 编码。

### 3.1 示例

服务器内部 JSON：

```json
{"v":"1","s":{}}
```

传输游标：

```
cx:cursor:eyJ2IjoiMSIsInMiOnt9fQ
```

## 4. 验证规则

服务器 MUST 在接收时验证游标：

1. **前缀检查**：游标必须以 `cx:cursor:` 开头
2. **Base64URL**：其余部分必须是合法的 Base64URL
3. **版本检查**：解码后的 `v` 必须是支持的版本
4. **过期检查**：解码后的 `x` 必须在未来（允许 5 分钟时钟偏差）
5. **结构**：解码后的内容必须是合法 JSON
6. **Space ID**：所有 space ID 必须是合法的 `cx:space:*` 格式
7. **事件 ID**：因果前沿中的所有事件 ID 必须合法
8. **HLC 格式**：时间线排序必须是合法的 HLC 格式

非法游标 MUST 被拒绝，返回 `invalid_cursor` 错误。

## 5. 游标演进

### 5.1 版本 1

初始版本，包含 space 位置、因果前沿和设备位置。

### 5.2 未来版本

新游标版本：

- MUST 使用不同的 `v` 值
- MUST 提供明确版本过渡或迁移方案
- SHOULD 支持优雅降级

## 6. 安全考虑

1. **篡改检测**：服务器 SHOULD 对游标内容包含 MAC 或签名
2. **过期**：游标 MUST 过期以防止过期状态重放
3. **隐私**：游标可能泄露 space 访问模式；在敏感上下文中应加密
4. **大小限制**：服务器 MAY 拒绝编码后超过 4KB 的游标
5. **对客户端不透明**：客户端 MUST NOT 检查游标内部结构 — 这防止信息泄露和耦合

## 7. 实现说明

### 7.1 客户端行为

- 始终使用最新的 `next_batch` 游标
- 本地存储游标以支持恢复
- 处理 `cursor_expired` 时开始全新同步
- 绝不修改或检查游标内容

### 7.2 服务器行为

- 每次同步响应后生成新游标
- 包含所有必要的状态位置
- 设置适当的过期时间（推荐：7 天）
- 在恢复请求时验证游标

### 7.3 压缩

对于拥有大量 space 的大型账户，服务器 MAY 使用压缩：

- 在 Base64URL 编码前应用 gzip
- 添加 `c=gz` 标志表示压缩
- 客户端必须支持解压缩（透明的，因为游标仍然不透明）

## 8. 一致性

声称支持 Contrix v1 同步的实现 MUST：

- 以不透明字符串形式接受和传输版本 1 游标
- 服务器 MUST 在接收时验证所有游标字段
- 客户端 MUST NOT 解析游标内容
- 支持每个游标至少 50 个 space
- 支持最长 7 天的过期时间
- 以适当错误拒绝非法游标

## 9. 示例

### 9.1 初始同步

不带 `since` 的请求：

```json
{}
```

响应带首个游标：

```json
{
  "next_batch": "cx:cursor:eyJ2IjoiMSIsInMiOnt9fQ",
  "spaces": {...}
}
```

### 9.2 恢复同步

带游标的请求：

```json
{
  "since": "cx:cursor:eyJ2IjoiMSIsInMiOnt9fQ"
}
```

### 9.3 过期游标错误

响应：

```json
{
  "error": "cursor_expired",
  "error_description": "提供的游标已过期。请执行初始同步。",
  "retry_after_ms": 0
}
```
